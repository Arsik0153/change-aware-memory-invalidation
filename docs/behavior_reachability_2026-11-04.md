# Цикл неограниченного сохранения ложной памяти при скрытой зависимости

В конечной модели найден достижимый цикл, на каждом переходе которого исходник
меняется, но hidden_missing не проверяет claim и сохраняет ложную запись доступной.
Поэтому внутри этой модели нет конечной верхней границы числа последующих коммитов,
на протяжении которых ложная память может оставаться доступной. Это не оценка
вероятности такого поведения в реальных проектах.

## Модель и проверяемая проекция состояния

Программа содержит `f`, возвращающую 1, 2 или результат `g()`, и `g`, возвращающую
1 или 2. Посторонний файл содержит `VALUE = 0` либо `VALUE = 1`.
Полное декартово произведение даёт 12 программ. Начальное состояние:
`f→g`, `g→1`, `VALUE=0`, claim `f()==1` доступен.

Состояние проверки — пара `(program_id, available)`. Допустим переход к любой
из 12 программ, в том числе без изменения текста. Обход продолжается до замыкания
достижимого множества; глубина истории заранее не ограничивается.

Использованы production-функции `select_claims` и `advance_state`, текущие index,
compare_indexes и hash-based masking. На границе validation результат задаёт
отдельный finite AST oracle. Docker-пробы в этой проверке не выполняются;
их фактическое число равно нулю. Программные snapshots сконструированы,
а не прочитаны из Git. Весь исходный текст и Git blob hashes сохранены.

Проекция достаточна для проверяемой доступности, потому что текущий selector
читает из прежнего MemoryState только available. Остальные аргументы определяются
парой исходных программ и фиксированными claim/provenance/config. Если запись
выбрана, следующий available определяется oracle verdict; иначе сохраняется прежнее
значение. last_checked_commit, last_supported_commit и basis в этой абстракции
не доказываются. Это аргумент по текущему коду, а не механизированное доказательство
эквивалентности произвольной реализации и модели.

## Результаты полного обхода

| Вариант | Достижимые состояния | Проверенные переходы | Ложная доступность | Ложное скрытие |
| --- | ---: | ---: | ---: | ---: |
| all_validate | 12 | 144 | 0 | 0 |
| intact | 12 | 144 | 0 | 0 |
| known_missing | 12 | 144 | 0 | 0 |
| hidden_missing | 14 | 168 | 2 | 0 |

Всего проверены 50 состояний и 600 переходов четырёх систем. Это размеры
достижимых графов, не независимые статистические наблюдения. Два ошибочных
состояния hidden_missing отличаются только значением посторонней переменной.

Кратчайший найденный префикс ошибки — изменение `g:1→2` при неизменной `f`.
Удалённое ребро `f→g` скрывает причину изменения истины. Затем:

`g=2, VALUE=0, available=true` → `g=2, VALUE=1, available=true`
→ `g=2, VALUE=0, available=true`.

На двух рёбрах цикла меняется unrelated.py, selection=false, reasons=[],
oracle даёт2. Повторяя этот цикл, получаем истории произвольной длины с ложной
доступностью. Аргумент относится к проекции: Git commit IDs и metadata lineage
могут продолжать меняться, не влияя на решение selector в этой модели.

## Контроли и отдельная сверка

Если скрыть ребро в варианте intact, требование отсутствия ошибок нарушается:
появляются два состояния ложной доступности. Если скрытой provenance дополнительно
отключить previously_unavailable, возникают ещё два состояния ложного скрытия.
Оба отрицательных контроля обнаружены. Это подтверждает роль повторной проверки
ранее скрытой записи в восстановлении, но не исправляет ложную доступную память.

Отдельный stdlib-only аудитор не импортирует CAMI. Он проверяет все 600 переходов
по явному правилу для данной грамматики: all/known проверяют всегда; остальные
проверяют ранее недоступную запись или изменившееся тело f; intact дополнительно
видит изменение g, когда f вызывает g. Проверяются полнота 12 successors для
каждого состояния, достижимость, oracle values, исходный текст, blob identities
и цепочка до найденного цикла. Пять подмен артефактов отклонены даже с пересчитанными
hashes: изменение selection, удаление successor, повреждение cycle edge,
удаление цикла и удаление свидетелей ошибочных состояний.

План закреплён в f339152, runtime — 64d0f19. Source snapshots совпали.
49 профильных тестов прошли. Первоначальный запуск аудитора ошибочно сравнивал
SHA-256 исходного форматированного protocol с его канонической копией; это
различие сериализации исправлено явным чтением original protocol и сравнением
его содержимого с копией. Результаты основного обхода не изменялись.

Проверка и аудитор написаны одним ассистентом: раздельная формула не является
независимым человеческим review. Выводы не распространяются на произвольный Python,
ошибки Docker, flakiness, changing config, неполную truth-разметку или cost model.

## Воспроизведение

Обход: `.venv/bin/python -m scripts.check_behavior_reachability --out runs/NEW_NAME`.
Аудит: `.venv/bin/python scripts/audit_behavior_reachability.py --input runs/NEW_NAME --out audit-NEW.json`.
Исходный frozen protocol берётся из examples/behavior_dependency/reachability_protocol.json;
параметр --protocol позволяет явно указать его переносимую копию.

Данные: `reports/research-20261104/behavior-reachability-v1/`.
Аудит и отрицательные контроли расположены рядом. Конечное воспроизведение
ниже не заменяет аргумент о цикле.

## Воспроизведение свидетеля в Git и Docker

Извлечённый префикс и один оборот цикла закреплены отдельным планом в b8a804d
до запуска. В конце добавлено восстановление `g→1`: это отдельный terminal step,
который не относится к опасному циклу и обеспечивает supported item для scorer.

Созданы пять разных Git commits: parent, скрытая порча g, VALUE:0→1, VALUE:1→0,
восстановление g. Git trees после порчи и после оборота цикла совпали; обе стороны
цикла изменяют только unrelated.py. Последнее дерево совпало с parent.

В all_validate, intact и known_missing выполнено по четыре maintenance validations;
ошибок доступности нет. После обнаруженной порчи intact перепроверяет оба
посторонних изменения по причине previously_unavailable. В hidden_missing
maintenance validations нет: available остаётся true на всех шагах, last_checked
остаётся parent, три ложных состояния доступны, после восстановления истина
возвращается без новой проверки. Все selection reasons hidden_missing пусты.

Выполнены 48 реальных probe executions: 21 passed и 27 ожидаемых assertion failures.
Технических отказов нет. Сверены 251 artifact hash, 62 input hashes, raw payloads,
полная lineage состояний и равенство source snapshots до/после. Результаты:
`reports/research-20261104/behavior-cycle-witness-v1/`; полный запуск:
`runs/behavior-cycle-witness-20261104-v1/`.

Воспроизведение: `.venv/bin/python -m scripts.check_behavior_history --protocol examples/behavior_dependency/cycle_witness_protocol.json --out runs/NEW_NAME`.

Наличие одного фактического оборота подтверждает соответствие свидетеля
исполняемой реализации на этом примере. Вывод о произвольно длинном сохранении
ошибки основан на конечном цикле и аргументе достаточности проекции состояния,
а не на выполнении бесконечного числа Docker-запусков.
