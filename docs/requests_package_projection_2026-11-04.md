# Requests: восстановление parent-проверки через проекцию пакета

В отдельной диагностике среды все 22 исторических Requests-parent выполнили
неизменённый frozen probe успешно по три раза: 66 passed, без технических отказов.
План закреплён в 57f01f6 до реализации; выполнение — на e0c0c3f.
Это результат восстановления среды для конкретного probe, не независимая разметка.

## Почему понадобился отдельный вариант

В full-tree диагностике 29 октября Requests дал 21 supported и один environment_error
до исполнения. Parent `e18879932287c2bf4bcee4ddf6ccb8a69b6fc656`, группа
`requests-ec6e9c57fcb5`, содержит символьные ссылки в `tests/certs/mtls/client/`.
Production materializer намеренно отклоняет такие записи. Замороженный probe
вызывает `requests.utils.unquote_unreserved('%7euser%2F')` и ожидает `'~user%2F'`.
Его код не менялся.

Новый заранее записанный вариант включает все Git blobs под `requests/` и
`src/requests/`, сохраняет их bytes и mode, исключает остальное дерево и пишет
полный список включений/исключений с object ID, SHA-256 и ограничениями.
Обе исходные символьные ссылки находятся вне пакета; ни одна не разрешалась
в путь на машине. Неподдерживаемая запись внутри пакета по-прежнему приводит
к отказу materialize — это проверено тестом.

Образ и Python остались такими же, как в предыдущей v3-диагностике:
`cami-parent-probes@sha256:4b6d3d7c0cf8a19e9c3574f9acc19a1876bda76da9544b6e7a81216fd0f0e916`,
Python 3.9.25. Образ не содержит установленного Requests, что проверено отдельным
изолированным запуском без repository mount. Probe исполняется в контейнерах без
сети, с read-only mounts, непривилегированным пользователем и лимитами ресурсов.

## Что подтверждено артефактами

- 22 группы, 66 raw JSON payloads с passed; неудобный parent не исключён.
- 396 записей включённых исходных файлов, соответствующих 144 уникальным Git blobs.
  SHA-256 всех уникальных blobs отдельно сверены с `git cat-file --batch`.
- 179 artifact hashes и 66 input hashes сверены после завершения.
- Снимки исходников до и после совпали; claims и frozen probes не изменились.
- 15 профильных tests, Ruff и mypy прошли.

Все проверки здесь выполнены тем же агентом. Отсутствие установленного Requests
исключает обычную подмену импортируемого пакета установленной копией, но не является
полным same-process трассированием всех импортированных зависимостей.

## Что результат не разрешает

Полный repository snapshot и package-only projection — разные контексты исполнения.
Production validator не изменён и по-прежнему отклоняет исходный full-tree snapshot
с символьными ссылками. Положительный результат проекции не является основанием
скрытно повторно использовать receipt, validation cache key или допуск старого профиля.
Драйвер не использует кэш и не пишет receipts, child labels или policy runs.

Для применения варианта в основном исследовании потребуется явно закрепить
проекцию и её происхождение в admission/execution protocol, провести независимую
parent-проверку и только затем freeze. Один конечный probe не подтверждает полную
совместимость исторического Requests или возможность исполнения его тестового набора.

## Воспроизведение

```bash
.venv/bin/python -m scripts.check_requests_projection \
  --out runs/requests-projection-NEW
```

Нужны закоммиченные исходники, восстановленные parent-only candidates и локальные
Git-репозитории по путям frozen plan, Docker и уже установленный образ.
Raw run: `runs/requests-projection-20261104-v1`.
Компактные manifests, observations, summary и отдельные файлы ранее заблокированного
parent: `reports/research-20261104/requests-projection-v1/`.

## Повторная проверка без Docker

```bash
.venv/bin/python scripts/audit_requests_projection.py \
  --run runs/requests-projection-20261104-v1 \
  --out reports/requests-projection-audit-NEW.json
```

Этот отдельный verifier использует только стандартную библиотеку и Git. Он
сверяет полный состав parent tree, включения/исключения проекции, hashes исходников,
claim identity, frozen probe, Python version, pytest node ID и setup/call/teardown
в каждом сыром stdout с summary. Он ограничен завершённым успешным диагностическим
прогоном и не предназначен для оценки произвольных failures. Требуются исходные
candidate files и локальный Git; контейнеры повторно не запускаются.

Проверены четыре отрицательных контроля: изменение payload, удаление записи
из дерева, подмена claim ID и изменение exit_code в stdout. Последние три случая
отклонены даже после пересчёта затронутых artifact hashes. Python с отключёнными
assertions (`-O`) явно отклоняется до создания отчёта. Финальный результат и
контроли сохранены рядом с остальными свидетельствами. Это проверка согласованности
артефактов, а не независимое удостоверение авторства или факта исполнения.
