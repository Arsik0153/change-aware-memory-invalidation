# Техническое задание для разработки системы проверки памяти

Версия 1.0. Дата 30 сентября 2026 года. Рабочее имя программы CAMI, пакет Python `cami`, команда `cami`.

Этот документ передаётся ИИ-разработчику целиком. Он задаёт реализацию исследовательского прототипа Change-Aware Memory Invalidation for LLM Coding Agents. Предыдущая переписка для начала работы не нужна. На момент составления в проекте есть исследовательское предложение и сборщик документов, но нет исследовательской программы, датасета или результатов.

## 1. Задача для ИИ разработчика

Реализуй локальную программу, которая хранит проверяемые утверждения о Python-репозитории, выбирает их для повторной проверки после изменений Git и сравнивает стоимость и качество разных способов обслуживания памяти.

Следуй этапам в разделе 15. Начни с работающего сквозного примера без LLM. После каждого этапа запускай соответствующие проверки, исправляй ошибки и записывай фактическое состояние реализации. Не останавливайся после создания каркаса. Заверши обязательные этапы M0–M5, если среда позволяет. M6 является отдельным расширением.

Не спрашивай пользователя о выборе библиотек, архитектуры, формата файлов или порядке работ. Эти решения приняты ниже. Если отсутствует внешний ресурс, выполни независимую работу и явно укажи блокировку. Не выдумывай API-ключи, экспериментальные данные, человеческие аннотации и результаты запусков.

Существующие `research_proposal.md`, `docs/submission_review.md`, `output/submission/` и сборщик документов сохраняй. Не переписывай научный текст и не пересобирай документы в рамках разработки программы. При существенном расхождении с предложением запиши его в `docs/implementation_status.md`.

Обычные детали реализации выбирай самостоятельно в пределах этого контракта. Изменение смысла метрик, границ датасета или правил доступа к эталонным ответам является изменением протокола. Записывай такие изменения до новых экспериментов и увеличивай `protocol_version`.

## 2. Исследовательский вопрос и границы выводов

Исследуй, когда выборочная перепроверка уменьшает полную стоимость обслуживания памяти при сопоставимых долях пропущенных устаревших и сохранённых правильных утверждений. Отдельно измерь поведение при неполных зависимостях и последовательных изменениях кода.

Выбор потенциально затронутого утверждения не доказывает его ложность. Решение валидатора не является эталонной разметкой. Утверждение, которое не проверяли на текущем коммите, может остаться доступным по политике, но не считается заново подтверждённым.

Первая версия обслуживает фиксированный набор утверждений. Она не генерирует и не переписывает память во время эксперимента. Поэтому выводы относятся к обслуживанию фиксированного набора, а не ко всему жизненному циклу обучающегося агента.

В обязательный объём входят CLI, Git-снимки, AST-индекс, утверждения, валидаторы, политики отбора, последовательные запуски, независимая оценка и воспроизводимые отчёты. Не добавляй веб-интерфейс, сервер, MCP, векторную базу, embeddings, оркестратор агентов, поддержку других языков или автоматическое исправление исходного кода.

Исследование пока не доказывает улучшение решения задач coding agent. Измерение доступности правильных утверждений само по себе не подтверждает их полезность для конкретной задачи.

## 3. Принятые технические решения

| Область | Решение |
|---|---|
| Среда программы | Python 3.12, Linux и macOS |
| Установка | `uv`, `pyproject.toml`, фиксируемый `uv.lock`, layout `src/` |
| CLI | Стандартный `argparse` |
| Внешние схемы | Pydantic 2, строгая валидация, `extra="forbid"`, поле `schema_version` |
| Внутренние данные | Типизированные неизменяемые записи; без словарей с неявной структурой |
| Хранение | UTF-8 JSON и JSONL, отдельный неизменяемый каталог каждого запуска |
| Git | Установленный Git через `subprocess` с массивом аргументов, без `shell=True` |
| Анализ Python | Стандартный `ast`, исходный код не импортируется |
| Зависимости | Собственный небольшой граф на словарях множеств, без графовой БД |
| Проверки проекта | `pytest`, `ruff`, `mypy`; зафиксированные версии в lockfile |
| Статистика | `numpy` для воспроизводимой выборки и bootstrap |
| Отчёты | JSON, CSV и Markdown; графики через `matplotlib` в экспериментальном этапе |
| Исполнение исследуемого кода | Docker с заранее подготовленным образом и отключённой сетью |
| LLM | Необязательный адаптер OpenAI; основной прототип работает без ключей и сетевых вызовов |

Зафиксируй конкретные совместимые версии зависимостей при первом разрешении и сохрани lockfile. Не используй плавающий `latest` в воспроизводимых запусках. Среда исследуемого репозитория может иметь другую версию Python внутри контейнера; записывай её отдельно от Python анализатора.

Один процесс владеет одним каталогом запуска. Параллельные политики используют разные каталоги. SQLite не нужен для первой версии: входы и результаты должны читаться без работающего сервиса и без скрытого состояния базы.

## 4. Пользовательский сценарий и команды

Реализуй следующие команды. Пути ниже являются контрактом будущих создаваемых примеров, а не утверждением о существующих файлах.

```bash
uv sync --locked --extra dev
uv run cami demo --out runs/demo
uv run cami check-inputs --config examples/demo/run.json
uv run cami run --config examples/demo/run.json --out runs/example
uv run cami score --run runs/example --labels examples/demo/labels.jsonl --out reports/example
uv run cami compare --runs runs/keep runs/all runs/file runs/symbol --labels data/evaluation/labels.jsonl --out reports/comparison
uv run pytest
uv run ruff check .
uv run mypy src/cami
```

`demo` создаёт собственный временный Git-репозиторий с известной историей, запускает несколько политик и сохраняет отчёт. Демонстрационные данные явно помечаются `synthetic`. Команда не требует Docker, ключа API или сети. Поведенческие проверки стороннего репозитория включаются только отдельной конфигурацией.

`check-inputs` проверяет схемы, уникальность идентификаторов, существование коммитов и цепочку переходов. Она не исполняет исследуемый код и не обращается к LLM.

`run` принимает один коммит основания и список следующих коммитов. Список из одного элемента означает обычную пару ревизий. Каждый следующий коммит должен иметь предыдущий первым родителем; merge-коммиты в версии 1 отклоняются. Для независимых пар выполняются независимые запуски с отдельными наборами памяти.

`score` является отдельным процессом. Только он читает `labels.jsonl`. `compare` проверяет совместимость входов, протокола и эталонной разметки, затем объединяет результаты. Не сравнивай разные популяции утверждений без явного раздельного отчёта.

Коды завершения: `0` означает завершённую операцию, `2` ошибку входа, `3` недоступный обязательный ресурс, `4` прерванный или незавершённый запуск. Отдельное `insufficient_evidence` является результатом проверки и само по себе не меняет код `0`.

Если `--out` уже существует, заверши команду с ошибкой без перезаписи. Автоматическое возобновление в версии 1 не реализуй. После аварии повторный запуск получает новый каталог и может использовать валидный кеш.

### 4.1 Конфигурация запуска

Все относительные пути конфигурации разрешаются относительно её файла. `check-inputs` и `run` используют одну схему. Генератор demo создаёт следующий файл с настоящими object IDs вместо показанных заглушек:

```json
{
  "schema_version": 1,
  "protocol_version": "1.0",
  "repo": {"repo_id": "demo", "path": "repo", "source_roots": ["."]},
  "parent_commit": "RESOLVED_PARENT_COMMIT",
  "child_commits": ["RESOLVED_CHILD_COMMIT"],
  "claims_path": "claims.jsonl",
  "provenance_path": "provenance.jsonl",
  "parent_receipts_path": "parent_receipts.jsonl",
  "scenario_id": "intact",
  "dataset_kind": "synthetic",
  "split": "development",
  "stratum": "fixture",
  "policy": {"id": "symbol_validate", "dependency_depth": 1},
  "validation": {"execution": "disabled", "llm": "disabled"},
  "allow_network": false,
  "max_calls": 0,
  "seed": 42
}
```

`dataset_kind` принимает `synthetic` или `real`; `split` принимает `development` или `heldout`; `stratum` принимает `fixture`, `chronological`, `enriched` или `replay`. Для реального replay длина `child_commits` больше одного. Лимиты и параметры, не указанные в примере, берутся из фиксированных defaults этого документа и разворачиваются в итоговом manifest.

`validation.execution` принимает `disabled` или `docker`; при `docker` обязательны environment profiles с digest образа и условиями монтирования. `validation.llm` принимает `disabled` или `openai`; при `openai` обязательны разрешение сети, бюджет и разрешённый model ID. Поле labels в конфигурации запуска запрещено.

Дополнительные поля RunConfig: `preview=false`, `replicate_id=0`, `cache_dir=null`, `environment_profiles={}`, `extra_environment_paths=[]`. При `cache_dir=null` общий кеш отключён. Явный cache path используется для разделения зафиксированных verdicts между политиками. Cache key всегда включает `replicate_id`; AST-кеш не зависит от этого поля. При `preview=true` отсутствующие валидаторы допускаются, но `evaluation_eligible=false`. Для сравнения stochastic LLM policies общий кеш обязателен; некешированный timing experiment оформляется отдельно. Контекст evidence не зависит от policy и её предыдущего verdict.

В M5 добавь команды `cami annotate-export --dataset DATASET --out DIR`, `cami annotate-import --input FILE --out DIR` и `cami freeze --dataset DATASET --out DIR`. Freeze создаёт запечатанный manifest с hashes входов; он не запускает исследуемую систему. Dataset manifest перечисляет run configs, splits, clusters и общую версию протокола. Он не подменяет отдельные run configs.

В M4 добавь `cami prepare-scenario --dataset DATASET --mode MODE --drop FRACTION --seed SEED --out DIR`. Команда создаёт публичный вариант provenance и графов. Для такого run обязательно дополнительное поле `graph_views_path`, указывающее на каталог графов по ревизиям. Полный граф и журнал удалений остаются в отдельном исследовательском каталоге.

## 5. Форматы данных

Все записи имеют `schema_version=1`. JSONL содержит одну самостоятельную JSON-запись в строке. Дубликаты ключей, ID и неизвестные поля являются ошибкой. JSON не содержит `NaN` или бесконечностей. Недоступная метрика записывается `null` вместе с причиной.

Идентификатор репозитория `repo_id` задаётся в dataset manifest и не зависит от локального пути. Git refs разрешаются в полные object IDs перед началом запуска. Не предполагай, что Git всегда использует SHA-1. Пути внутри репозитория относительные POSIX, без `..`, абсолютных путей и перехода через symlink за пределы снимка.

### 5.1 Неизменяемое утверждение Claim

| Поле | Смысл |
|---|---|
| `claim_id` | Уникальный стабильный ID из входного набора |
| `repo_id`, `origin_commit` | Репозиторий и ревизия, на которой утверждение изначально подтверждено |
| `kind` | `symbol_exists`, `signature_equals`, `behavior_test` или `prose` |
| `text` | Одно утверждение с явно ограниченной областью действия |
| `subject` | Точная идентичность объекта, `path`, `qualname`, `node_kind` |
| `predicate` | Типизированные параметры проверки, вариант определяется `kind` |
| `scope` | Границы вывода: точное определение, конечный тестовый случай или ограниченное текстовое утверждение |

Вся запись Claim после начала эксперимента неизменяема. Сохраняй SHA-256 канонического содержимого записи. При повторном использовании ID с другим содержимым отклоняй вход. Канонизация использует сортировку ключей, UTF-8, компактные разделители и исходные Unicode-строки без неявного исправления. Provenance и подтверждение parent находятся в отдельных файлах, чтобы её маскирование не меняло утверждение и не раскрывало удалённые связи через исходную запись.

Формальный предикат определяет область вывода для первых трёх типов. Текст обязан соответствовать предикату. Один успешный тест подтверждает только зафиксированный тестовый случай, а не универсальное утверждение о поведении функции.

### 5.2 Источники Provenance

Anchor имеет `path`, необязательные `qualname` и диапазон строк, `scope` со значением `symbol` или `file`, `observed_commit`, `content_hash` и `origin` со значением `manual`, `static` или `runtime`. Диапазон строк служит для отображения, но не является устойчивой идентичностью.

Provenance содержит `anchors`, список явных зависимостей, `known_incomplete: bool` и `unresolved_reasons`. `known_incomplete=false` означает отсутствие известных пропусков, а не доказанную полноту.

`provenance.jsonl` содержит записи `schema_version`, `claim_id`, `scenario_id` и поля provenance. Внутри одного scenario исходная запись неизменяема. Скрытая каноническая версия хранится вне входного каталога run. Parent receipt содержит `claim_id`, `origin_commit`, `status=supported`, тип и hash независимого подтверждения. Policy получает только факт допуска в cohort, а не содержимое parent receipt.

Явная dependency-запись содержит `from`, `to`, `relation` и `origin`. Узел задаётся path и необязательным qualname. `relation` принимает `calls`, `imports` или `evidence_dependency`. Отсутствие доказанной связи не превращается в утверждение о независимости.

Текущее местоположение evidence хранится в состоянии отдельно от исходной записи. Обновление evidence не изменяет смысл claim. Нельзя автоматически заменить старое имя функции новым только потому, что тела похожи. Утверждение о точном старом имени при его исчезновении больше не подтверждается.

В версии 1 точная идентичность определяется `path + qualname + node_kind`. Разрешены функции и методы с лексически однозначными определениями. Повторные определения, условные определения и динамические присваивания регистрируются как неоднозначность. Не выбирай первое совпадение молча.

### 5.3 Verdict и событие проверки

Валидатор возвращает `supported`, `contradicted` или `insufficient_evidence`. Событие содержит `claim_id`, текущий commit, тип валидатора, reason code, использованное evidence, hash входа проверки, длительность, потребление ресурсов и ссылки на журналы.

Отдели `reason=predicate_mismatch` от `reason=timeout`, `parse_error`, `environment_error`, `evidence_truncated`, `ambiguous_subject` и `provider_error`. Техническая ошибка никогда не превращается в `contradicted`.

`subject_absent` допустим только при однозначном отсутствии точного объекта в успешно прочитанном снимке. Неудачный импорт, неизвестный alias или ошибка парсинга не доказывают отсутствие объекта.

### 5.4 Состояние памяти MemoryState

Храни `claim_id`, `revision`, `state`, `last_checked_commit`, `last_supported_commit`, `last_verdict`, `basis`, `current_provenance`, `available` и `withheld_reason`.

`state` принимает `valid`, `needs_validation`, `stale`, `retired`. `basis` принимает `validated`, `carried_forward` или `heuristic`. Поле `available` отдельно отражает решение политики о доступности. Удаление всей памяти не является доказательством ложности утверждений.

`last_checked_commit` меняется только при реальной проверке. `last_supported_commit` меняется только после `supported`. Перенос доступного утверждения вперёд по версии не обновляет эти поля.

### 5.5 Пример утверждения

Ниже пример формы записи. Строки `RESOLVED_PARENT_COMMIT` и `GENERATED_SOURCE_HASH` заменяет генератор демонстрации. Такие заглушки не разрешены в реальных входах.

```json
{
  "schema_version": 1,
  "claim_id": "demo-symbol-001",
  "repo_id": "demo",
  "origin_commit": "RESOLVED_PARENT_COMMIT",
  "kind": "symbol_exists",
  "text": "В math_ops.py определена функция add.",
  "subject": {"path": "math_ops.py", "qualname": "add", "node_kind": "function"},

  "scope": "Точное синтаксическое определение функции в указанном файле."

```

Связанная запись `provenance.jsonl`:

```json
{
  "schema_version": 1,
  "claim_id": "demo-symbol-001",
  "scenario_id": "intact",
  "anchors": [{"path": "math_ops.py", "qualname": "add", "scope": "symbol", "observed_commit": "RESOLVED_PARENT_COMMIT", "content_hash": "GENERATED_SOURCE_HASH", "origin": "static"}],
  "dependencies": [],
  "known_incomplete": false,
  "unresolved_reasons": []
}
```

## 6. Чтение Git и анализ изменений

Читай содержимое по object IDs через Git без переключения пользовательской рабочей копии. Не выполняй checkout, reset, clean или stash в исходном репозитории. Рабочие незакоммиченные изменения не входят в исследуемые снимки.

Используй NUL-разделённый вывод Git для списков путей. Отключи внешние diff-драйверы и textconv. Rename detection является подсказкой для отчёта, а не доказательством идентичности. Добавления и удаления входят в набор изменений. Submodules и Git LFS payload в версии 1 не поддерживаются; соответствующее evidence получает диагностируемое ограничение.

AST-индекс хранит определения, сигнатуры, нормализованные AST-hashes, module-level imports и разрешимые вызовы. Нормализованный AST не содержит координат строк, но сохраняет строковые литералы и docstrings. Не называй равенство AST доказательством семантической эквивалентности.

Сигнатура включает порядок и имена positional-only, positional-or-keyword и keyword-only параметров, `*args`, `**kwargs`, наличие и AST значений по умолчанию, аннотации, async-признак и декораторы. Это синтаксическая сигнатура определения, а не результат `inspect.signature` во время исполнения. Комментарий или форматирование не меняют её.

Сериализация ожидаемой сигнатуры имеет поля `parameters`, `returns_ast`, `decorators_ast`, `is_async`. Параметр содержит `name`, `kind`, `default_ast`, `annotation_ast`. Отсутствующее значение представляется `null`, а выражение `None` представляется AST, поэтому эти случаи различимы. `kind` принимает `positional_only`, `positional_or_keyword`, `var_positional`, `keyword_only`, `var_keyword`. AST выражения сериализуется `ast.dump(..., include_attributes=False)` и зависит от версии анализатора.

Граф использует направленное ребро `consumer -> dependency`. Начальные поддерживаемые связи: однозначный вызов функции в том же модуле и явный импорт известного символа из индексируемого модуля. Вызовы через вычисляемые атрибуты, monkey patching, `import *`, неоднозначные re-exports и динамические imports не разрешай предположениями.

Для выбора затронутых consumers проходи граф в обратном направлении от изменившихся объектов. Используй объединение рёбер старого и нового снимков, чтобы не потерять удалённую зависимость. Устраняй циклы множеством посещённых узлов. Глубина по умолчанию равна 1; абляции используют 0 и 2.

Неразрешённая связь в поддерживающем подграфе конкретного claim запускает консервативную проверку этого claim на каждом переходе. Если область влияния определить невозможно, проверь все behavioral и prose claims данного репозитория. Записывай частоту такого fallback, даже если он уничтожает экономию.

Изменения конфигурации окружения выбирают все behavioral и prose claims. Список по умолчанию включает `pyproject.toml`, `setup.py`, `setup.cfg`, requirements-файлы, lockfiles, `tox.ini`, `pytest.ini`, `conftest.py` и Dockerfile. Дополнительные файлы явно задаются в dataset manifest. Структурные claims проверяются по синтаксическому контракту.

Один файл больше 2 MiB, ошибка декодирования или неподдерживаемый синтаксис дают ограничение анализа. Не пропускай такой файл молча. Для связанных claims выбирай проверку, а при отсутствии доступного evidence возвращай `insufficient_evidence`.

Кеш AST имеет ключ из Git blob ID, версии Python и версии индексатора. Кеш результатов сравнения дополнительно зависит от пары commits и настроек графа.

## 7. Валидаторы

### 7.1 Структурные проверки

Для `symbol_exists` проверь наличие точного объекта в AST. Для `signature_equals` сравни нормализованную сигнатуру с сохранённой ожидаемой структурой. При неоднозначности возвращай `insufficient_evidence`.

Вариант predicate `symbol_exists` допускает только `expected=true` в версии 1. Вариант `signature_equals` содержит `expected_signature` указанной выше структуры. Вариант `behavior_test` содержит `probe_path`, `probe_sha256`, `node_id`, `environment_id`. Вариант `prose` содержит только `type=prose`; содержание и границы утверждения берутся из `text` и `scope`. Несовпадение `kind` и `predicate.type` отклоняется.

Объявление отсутствует после успешного анализа соответствующего снимка: `contradicted` с `subject_absent`. Объявление есть, но сигнатура другая: `contradicted` с `predicate_mismatch`. Любые ошибки чтения или парсинга: `insufficient_evidence`.

Не запускай исходный код для построения AST и получения сигнатур. Не передавай структурную проверку LLM.

### 7.2 Исполняемые проверки поведения

`behavior_test` содержит путь и SHA-256 отдельного probe-файла, точный pytest node ID, идентификатор подготовленной среды и описание проверяемого случая. Probe создан по родительской ревизии, заморожен и одинаков на всех следующих ревизиях.

Для внешнего репозитория исполняй probe в Docker. Репозиторий и probe монтируются read-only. Рабочий временный каталог находится внутри контейнера. Сеть отключена, корневая файловая система read-only, пользователь непривилегированный, capabilities удалены, включён `no-new-privileges`. Начальные лимиты: 2 CPU, 2 GiB памяти, 128 процессов, 60 секунд на probe. Профиль и digest образа входят в manifest.

Установка зависимостей выполняется при подготовке образа, вне измеряемого тестового запуска. Не устанавливай зависимости на хост и не выполняй repository setup scripts вне контейнера. Образ и окружение должны воспроизводимо работать для обеих сравниваемых ревизий либо иметь явно версионированные профили. Изменение среды учитывается в отчёте.

Перед допуском probe к данным требуется три успешных повторения на parent. Assertion failure считается `contradicted` только для успешно собранного и выполненного целевого теста. ImportError, collection error, timeout, crash, отсутствие Docker и ошибки зависимостей дают `insufficient_evidence`. Не интерпретируй общий ненулевой exit code pytest как опровержение claim.

В основной паре запускай probe три раза на child. Три успеха дают `supported`, три одинаковых содержательных провала assertion дают `contradicted`. Смешанные исходы дают `insufficient_evidence` с `flaky`. Сохраняй каждый результат. Не меняй probe для получения желаемого исхода.

### 7.3 Проверка текста через LLM

`prose` использует только LLM-адаптер. В offline-режиме этот вид возвращает `insufficient_evidence` с `validator_unavailable`, а run помечается неполным по покрытию валидаторов. Не изображай LLM через правила поиска ключевых слов.

Выбран один провайдер OpenAI через официальный Python SDK в extra `llm`. Реализуй один адаптер, без автоматического переключения провайдеров. Реальный model ID задаётся `CAMI_LLM_MODEL`, ключ через `OPENAI_API_KEY`. Не подставляй имя модели Codex из настроек ИИ-разработчика как предполагаемый API model ID.

Сетевые проверки включаются только флагом конфигурации `allow_network=true` и явным положительным бюджетом вызовов. По умолчанию `allow_network=false`, `max_calls=0`. Нет ключа, model ID или бюджета: диагностируй отсутствие ресурса и сохрани работоспособность offline-части. Выбор и доступность оплачиваемой модели являются внешним параметром запуска, а не нерешённой архитектурой.

Prompt получает неизменный claim, область утверждения и детерминированно построенный пакет текущего evidence. Не передавай эталонные labels, вердикты других политик, тестовые ожидаемые ответы или тексты будущих ревизий. Код и комментарии внутри evidence являются данными, а не инструкциями модели. Tool use для LLM-валидатора отключён.

Evidence включает точный subject, его anchors, объявленные зависимости и module-level imports. Порядок сортируется по пути и имени. Лимит версии 1 равен 24000 Unicode-символов исходного evidence. При превышении обязательного evidence не обрезай его незаметно, верни `insufficient_evidence` с `evidence_truncated` без LLM-запроса. Записывай также фактические API tokens.

Для API зафиксируй `max_output_tokens=2048` и generation settings в manifest до held-out запуска. Если выбранная модель поддерживает temperature, используй 0; если не поддерживает, поле не отправляется и это отражается в настройках. Не называй ни один из этих режимов гарантированно детерминированным. Не меняй модель или настройки автоматически после ошибки провайдера.

Ответ имеет строгую схему `verdict`, `reason`, `evidence_refs`. Ссылки должны указывать на переданное evidence. Невалидный JSON или ссылки вне пакета дают `insufficient_evidence`. Допустимы не более двух повторов только при временной транспортной ошибке, с учётом бюджета. Не повторяй содержательный ответ до получения желаемого результата.

Для сопоставления selectors используй общий неизменяемый кеш вердиктов с ключом из claim content hash, commit, evidence hash, версии валидатора, model ID, prompt hash и настроек генерации. Одна и та же проверка получает один сохранённый ответ независимо от policy. Policy не имеет доступа к вердиктам невыбранных claims. Отдельное изучение случайности LLM выполняется как новый эксперимент с новым replicate ID.

## 8. Политики и обновление состояния

Реализуй все политики из таблицы. Каждая получает только снимки, видимую provenance и предыдущие состояния. Эталонные labels и скрытая полная provenance недоступны интерфейсу policy.

| Policy ID | Правило |
|---|---|
| `keep_all` | Сохраняет исходную память доступной, без последующих проверок |
| `clear_all` | После первого перехода делает весь фиксированный набор недоступным; не перепроверяет и не восстанавливает |
| `file_invalidate` | При изменении файла anchor исключает claim без валидатора |
| `symbol_invalidate` | При изменении соответствующего AST-symbol исключает claim без валидатора |
| `all_validate` | На каждом переходе перепроверяет все исходные claims |
| `file_validate` | Перепроверяет claims с изменившимся файлом anchor и claims, требующие консервативной проверки |
| `symbol_validate` | Перепроверяет по AST-symbol, обратным зависимостям заданной глубины и консервативным правилам |

У прямых invalidation-baselines исключение необратимо до конца replay. Они не объявляют утверждение доказанно ложным: сохраняй `state=needs_validation`, `basis=heuristic`, `available=false`, `withheld_reason=heuristic_invalidation`. Для `clear_all` сохраняй последнее эпистемическое состояние, но устанавливай `available=false` и `withheld_reason=policy_reset`. Этим явно различаются стратегия отказа от памяти и подтверждённая ошибка.

У `file_invalidate` и `symbol_invalidate` известная неполнота, неразрешимость или ошибка анализа связанного evidence тоже исключают claim. Anchor с `scope=file` в symbol-policy использует file hash. Ни одна политика не заменяет symbol anchor файловым только ради улучшения результата; вид anchor фиксирован во входных данных.

Для проверяющих политик сначала выбираются изменённые claims. Дополнительно на каждом переходе выбираются все ранее недоступные claims. Это фиксированное правило позволяет обнаружить восстановление после revert и повторить проверку после недостаточного evidence. Учитывай его стоимость и долю в общем числе вызовов.

| Событие для проверяющей политики | Новое состояние и доступность |
|---|---|
| Claim выбран, проверка ещё не завершилась | `needs_validation`, недоступен |
| `supported` | `valid`, доступен, `basis=validated` |
| `contradicted` с `predicate_mismatch` | `stale`, недоступен |
| `contradicted` с `subject_absent` для точного структурного subject | `retired`, недоступен |
| `insufficient_evidence` | `needs_validation`, недоступен |
| Claim не выбран и ранее доступен | Доступность сохранена, `basis=carried_forward`, даты проверки не меняются |

`retired` в этом протоколе означает исчезновение точного объекта, указанного в структурном предикате. Оно не означает физическое удаление записи или универсальную невозможность восстановления. Если точный объект возвращается и проверка проходит, состояние снова становится `valid`. Варианты переноса на другой объект вне версии 1.

При старте все claims должны быть подтверждены на parent независимыми материалами. Preflight проверяет схему, наличие evidence и работоспособность среды; behavioral probe должен пройти три parent-повтора. Не требуй, чтобы исследуемый LLM-валидатор согласился с parent label, иначе cohort будет отобран под его собственные ответы. Неподтверждённый parent или отсутствие обязательного валидатора исключает claim из cohort до запуска всех политик. Причина исключения публикуется. Cohort одинаков для всех сравниваемых политик; его нельзя менять на child по результату одного метода.

В preview-режиме разрешено обрабатывать неполные входы, но такой run получает `evaluation_eligible=false` и не входит в основное сравнение. Начальные расходы проверки памяти учитываются отдельно и одинаково для всех политик.

Основной offline cohort содержит структурные и доступные поведенческие claims. Prose без работающего LLM-валидатора исключается до freeze, а не после просмотра результатов. Отсутствие API-ключа не препятствует M0–M5.

## 9. Неполная provenance

Добавь генератор вариантов входного набора с вероятностями удаления зависимостей `0`, `0.25`, `0.50`, `0.75` и seeds `17`, `42`, `73`. Для ребра вычисляй SHA-256 от канонической записи `repo_id`, `from`, `to`, `relation`, `seed`. Его целое значение, делённое на `2**256`, задаёт число `u` в диапазоне от 0 включительно до 1 исключительно. Ребро удаляется при `u < drop_fraction`. Это сохраняет решение для одной связи между ревизиями. Claim без связей не меняется; отчёт показывает фактическую долю воздействия, которая не обязана точно совпасть с параметром. Текст, anchors точного subject и формальный предикат не редактируются. Эта версия абляции исследует пропуски зависимостей, а не все возможные виды повреждения provenance.

В режиме `known_missing` после удаления выставляется `known_incomplete=true`. В режиме `hidden_missing` флаг не меняется. Генератор создаёт отдельный `provenance.jsonl` для scenario при неизменном `claims.jsonl`. Исходная полная provenance и список удалений доступны только генератору вариантов и scorer, но не policy и не валидатору.

В этой абляции скрытая связь также недоступна графовому отбору. Политика не должна восстановить удалённое ребро из общего немаскированного графа через другой интерфейс. Явно записывай, какие связи доступны после маскирования. Сам исходный код не редактируется; способность валидатора самостоятельно понять выбранный claim по доступному коду не запрещается.

Генератор вариантов создаёт graph view для каждого scenario вне исследуемого процесса. Engine получает только этот graph view; при режиме абляции повторная генерация полного графа внутри policy запрещена. Одинаковая маска действует на всех ревизиях replay для стабильных edge IDs. Новые наблюдаемые рёбра проходят то же детерминированное правило маскирования. Маскирование является управляемым экспериментом, а не заявлением, что реальная система знает о скрытом пропуске.

Нулевая доля должна воспроизводить исходный результат. Полное отсутствие anchors без указания причины трактуется как известная неполнота. Не выдавай идеальную полноту ручных связей за способность программы автоматически построить такую provenance.

## 10. Независимая разметка и данные

Эталонная запись имеет `claim_id`, `commit`, `label` из `supported`, `contradicted`, `uncertain`, идентификатор разметчика, evidence, тип подтверждения и статус adjudication. Начальная истинность на parent проверяется отдельно. Утверждение с неверным parent не становится положительным примером устаревания.

Не используй production-валидатор для автоматического создания эталонных labels. Для синтетических fixtures ожидаемые исходы задаются вручную по сценарию. Для структурного поднабора нужен независимый проверенный oracle, для поведения фиксированные проверенные тестовые случаи, для свободного текста человеческая разметка. Общие функции нормализации допустимы только если их использование раскрыто и не делает scorer копией проверяемого алгоритма.

Выбор enriched commits отделён от создания claims. Генератор claims видит только parent и фиксированное задание; ему не передаются diff, описание child и список изменённых symbols. Не выбирай удобные claims после просмотра результата политики.

Разметчики не видят policy outputs. Второй разметчик независимо проверяет не менее 20% основного набора. Сохраняй исходные ответы до согласования, долю совпадений и Cohen's kappa. При отсутствии второго человека технические эксперименты продолжаются, но отчёт явно отмечает single-annotator limitation.

Используй Click для разработки и пилота, Requests и pytest для held-out проверки. Полные repo URLs, commits, source roots и способ восстановления среды фиксируются в dataset manifest. Пилот начинается с 12 переходов Click и до десяти claims на переход. Если исторические среды не восстанавливаются, не заменяй репозиторий молча; запиши причину и новую версию протокола.

Основной запланированный набор содержит 60 пар commits, по 20 на репозиторий, и примерно 600 claims. В каждом репозитории половина переходов хронологическая, половина обогащённая изменениями API, исправлениями и рефакторингами. Страты анализируются раздельно. Не называй все 600 примеров held-out: данные Click являются development.

Планируемые replay-данные содержат три непересекающиеся последовательности по десять переходов из held-out репозиториев. Каждая начинается с десяти claims. Все исходные claims размечаются на всех ревизиях, включая уже исключённые. Эти данные не пересекаются с development и независимыми парами основного набора. При невозможности такого отбора уменьши объём с явной записью ограничения; не дополняй его синтетическими данными под видом реальных.

Пилот фиксирует частоту устаревания, число разных commits с устареванием, трудозатраты разметки и стоимость восстановления среды. До held-out запусков сохраняется `protocol.json` с окончательным cohort, параметрами, splits и их hashes. После просмотра held-out результатов настройки заморожены. Любое дополнительное исследование получает другой ID и отметку exploratory.

Размер 600 не является доказательством статистической достаточности. Если в отчётной страте меньше 50 contradicted случаев либо они происходят менее чем в 20 независимых commit-кластерах, программа помечает выводы о надёжности как exploratory. Это выбранное правило отчётности, а не гарантия мощности при превышении порога. Не увеличивай выборку до получения желаемой значимости.

## 11. Метрики и честное сравнение

Для одной ревизии обозначь `S` как множество эталонно поддержанных claims, `C` как опровергнутые, `U` как неопределённые, `A` как доступные по policy. Все множества относятся к одному исходному cohort.

| Метрика | Определение |
|---|---|
| `stale_exposure` | `len(A ∩ C) / len(C)` |
| `valid_retention` | `len(A ∩ S) / len(S)` |
| `available_contamination` | `len(A ∩ C) / len(A ∩ (S ∪ C))` |
| `selection_recall` | Число выбранных из `C`, делённое на `len(C)` |
| `false_invalidation` | Число claims из `S` с финальным `state` stale или retired, делённое на `len(S)` |
| `valid_withholding` | `len(S - A) / len(S)` |
| `uncertain_available` | Число claims из `A ∩ U`, отдельно от бинарных ошибок |

`stale_exposure` измеряет доступность устаревших записей, а не частоту их реальной выдачи пользователю. Для `selection_recall` у политик без валидатора выводи `null` с `not_applicable`. `false_invalidation` у прямых invalidation-baselines тоже `not_applicable`, поскольку они не выдают подтверждённый verdict. Их ущерб отражает `valid_withholding`.

Для precision, recall и F1 подтверждённой инвалидации множество predicted-positive `P` содержит claims с финальным `state` stale или retired и текущим проверенным `contradicted`. Тогда `TP=len(P ∩ C)`, `FP=len(P ∩ S)`, `FN=len(C - P)`. Claims с эталоном uncertain не входят в эти счётчики. Покажи дополнительный разрез stale и retired, но не меняй основное определение между политиками. Используй финальное решение текущей ревизии, а не количество повторных событий. Отдельно покажи результаты структурного, исполняемого и LLM-валидатора, включая `insufficient_evidence` и перенос непроверенных состояний. Нулевой знаменатель всегда даёт `null`, никогда условную единицу или ноль. При нулевых TP и ненулевых FP или FN F1 равен 0 по формуле `2*TP/(2*TP+FP+FN)`.

Основные графики показывают стоимость, `stale_exposure` и `valid_retention` совместно. `clear_all` не объявляется победителем только из-за нулевой exposure. До пилота не вводи выдуманный допустимый риск. Основной вывод версии 1 является описанием компромиссов. Pareto-доминирование требует не большей стоимости и exposure и не меньшей retention, хотя бы с одним строгим улучшением; это описание наблюдений, а не автоматически статистическая победа.

Отчёт содержит числители и знаменатели, результаты по репозиторию, страте, типу claim и режиму provenance. Micro-агрегат считается по суммам счётчиков; macro по репозиториям показывается отдельно. Не смешивай chronological и enriched rates в оценку естественной частоты устаревания.

Для независимых пар используй парный cluster bootstrap по commit, 2000 повторов и seed 42, с 95% интервалами. Если пары имеют пересекающуюся историю, заранее объединяй их в episode-кластеры. Повторная выборка кластера переносит все его claims и все сравниваемые политики вместе. Не вычисляй убедительно выглядящие интервалы из одной независимой группы. Три replay-последовательности показываются по отдельности без заявлений о точной популяционной оценке.

### 11.1 Полная стоимость

Записывай wall time, CPU time, число выбранных claims, логические проверки, фактически выполненные проверки, cache hits, test executions, input/output tokens, время построения и обновления индекса. Отдельно учитывай построение provenance и ручные минуты разметки. Человеческий труд не превращай в API tokens.

Одна выбранная пара claim/revision даёт одну logical validation. Cache hit даёт ноль actual validations. Одна actual validation поведенческого claim включает три test executions. Каждый сетевой повтор даёт дополнительный actual request и расходует `max_calls`; это ограничение относится к фактическим запросам, включая retries. Preflight, обслуживание и дополнительные replicates имеют отдельные счётчики. Ошибка до обращения к API не расходует запрос, но учитывает локальное время.

Раздели реальный расход текущего запуска и оценку стоимости политики без бесплатного общего кеша. При cache hit не записывай нулевую стоимость проверки как преимущество позднее запущенной политики. Сохраняй ссылку на исходное измерение и отмечай восстановленную стоимость. Оценку runtime из кеша не называй измеренным end-to-end временем.

Каждая политика оплачивает только необходимые ей операции. `keep_all` и `clear_all` не строят AST-индекс ради фиктивных расходов. `file_validate` не оплачивает граф вызовов, если он не нужен её evidence. `all_validate` строит evidence и исполняет проверки, но не оплачивает ненужный change selector. Общая реализация engine не должна навязывать всем политикам стоимость самого сложного метода.

Сравнивай холодный старт и обслуживание после построения индекса отдельно. Для финального времени выполняй отдельные некешированные прогоны в одинаковой среде с фиксированным порядком, перемешанным seed 42, и тремя повторениями. Если эти запуски не выполнены, отчёт содержит только доступные измерения.

Для проверки масштабирования используй размеры памяти 10, 100 и 1000 разных claims там, где такие данные доступны. Дубликаты одного claim не считаются независимыми научными примерами. Синтетическое увеличение нагрузки разрешено только как отдельно помеченный performance benchmark. Покажи накопленную стоимость по числу переходов и точку окупаемости индекса, если она наблюдается. Не выдумывай её, если выборочный метод нигде не дешевле.

## 12. Выходные файлы и воспроизводимость

Каждый успешный `run` создаёт следующий каталог:

```text
run/
  manifest.json
  claims.jsonl
  provenance.jsonl
  transitions.jsonl
  selections.jsonl
  validations.jsonl
  states.jsonl
  costs.jsonl
  evidence/
  logs/
```

`manifest.json` содержит schema/protocol versions, configuration hash, content hashes входов, repo object IDs, policy и параметры, версию приложения, Python, ОС, Git, образ контейнера, model и prompt IDs при наличии, seed, время начала и конца, статус и `evaluation_eligible`.

На каждый claim и revision имеется ровно одна финальная запись в `states.jsonl`, даже если claim не выбирался. Каждое решение выбора содержит reason codes. Выход сортируется по порядку перехода и `claim_id`.

`score` создаёт `metrics.json`, `per_claim.csv`, `summary.md`. `compare` дополнительно создаёт `comparison.csv`, интервалы и графики. Markdown-отчёт перечисляет исключённые данные, неизвестные labels, технические ошибки, непроверенные claims и ограничения выводов.

Сначала каталог имеет статус `running`. Файлы публикуются атомарно, итоговый manifest получает `complete` только после проверки полноты записей. Ошибка оставляет `failed` с причиной и сохранёнными журналами. Scorer отклоняет незавершённые запуски.

Одинаковые входы и сохранённые verdicts дают одинаковые решения и метрики. Временные отметки, durations и runtime IDs могут отличаться. Проверка воспроизводимости сравнивает канонические научные данные, а не байтовое равенство всех файлов.

Не записывай API-ключи и полное окружение процесса. Корпуса, локальные `.env`, кеши и `runs/` исключаются из Git. В репозитории сохраняются схемы, маленькие демонстрационные данные, код и manifests воспроизводимых наборов. Реальные корпуса публикуются только с сохранением применимых лицензий и ссылок на исходники.

## 13. Модули и границы ответственности

Создай следующую структуру. Допустимы небольшие внутренние файлы, но не дополнительные сервисные слои.

```text
src/cami/
  cli.py                # Аргументы и коды завершения
  models.py             # Форматы и инварианты записей
  repository.py         # Безопасное чтение Git-снимков
  index.py              # AST, signatures, зависимости и change set
  policies.py           # Выбор проверок и baselines
  validation.py         # Структурные и исполняемые проверки
  llm.py                # Необязательный сетевой адаптер
  engine.py             # Выполнение переходов и состояния памяти
  artifacts.py          # Атомарное хранение результатов и кеш
  evaluation.py         # Labels, метрики и bootstrap
  reporting.py          # CSV, Markdown и графики
tests/
examples/demo/
schemas/
docs/implementation_status.md
docs/annotation_guide.md
```

Основные интерфейсы:

```python
read_snapshot(repo: RepoLocation, revision: str) -> Snapshot
build_index(snapshot: Snapshot, config: IndexConfig) -> CodeIndex
compare_indexes(before: CodeIndex, after: CodeIndex) -> ChangeSet
select_claims(context: SelectionContext, policy: PolicyConfig) -> SelectionResult
validate_claim(claim: Claim, context: ValidationContext) -> ValidationResult
advance_state(previous: MemoryState, decision: ClaimDecision) -> MemoryState
run_experiment(config: RunConfig, output_dir: Path) -> RunManifest
score_run(run_dir: Path, labels: LabelSet) -> EvaluationReport
```

`SelectionContext` не содержит labels и кешированных verdicts. `ValidationContext` не содержит policy ID, чтобы evidence и ответы не зависели от сравниваемого метода. `evaluation.py` не вызывается из policy или validator. Глобальное изменяемое состояние запрещено. Не создавай универсальные base classes, registry plugins или dependency injection framework ради предполагаемых будущих расширений.

Публичный CLI скрывает детали индекса, кеша и переходов состояний. Исследователь выбирает manifest и policy, а не вручную координирует внутренние этапы программы.

## 14. Обязательные тестовые сценарии

Создай маленькие настоящие Git-репозитории во временных каталогах тестов. Ожидаемые ответы задай независимо от production-индексатора. Следующие сценарии проверяются через CLI или основной публичный интерфейс:

1. Изменение комментария сохраняет сигнатуру и AST-body hash, но меняет file hash.
2. Изменение сигнатуры опровергает `signature_equals`, но сохраняет `symbol_exists`.
3. Удаление точного символа делает структурный claim `retired`.
4. Изменение независимой функции не выбирает несвязанный claim при `symbol_validate`.
5. Изменение вызываемой функции выбирает claim вызывающей функции при depth 1, но не при depth 0.
6. Удалённое dependency-ребро не исчезает из анализа текущего перехода благодаря объединению графов.
7. Циклические зависимости завершаются и не дублируют проверки.
8. Rename не переносит утверждение о старом имени на новое.
9. Parse error и неоднозначное определение дают uncertainty, а не `supported` или `contradicted`.
10. Последовательность valid, stale, revert возвращает claim в valid у проверяющих политик.
11. `insufficient_evidence` исключает claim из доступных и вызывает повторную проверку на следующем переходе.
12. `carried_forward` не обновляет `last_checked_commit` и `last_supported_commit`.
13. `clear_all` сохраняет нулевую retention при наличии правильных claims; его contamination при пустой памяти равна `null`.
14. Known и hidden missingness не получают скрытые связи через общий граф или evaluation-модуль.
15. Перестановка запуска policies не меняет зафиксированные verdicts; cache hits не дают искусственной экономии в логическом сравнении.
16. Удаление или изменение labels не меняет результаты `run`, поскольку он не читает labels.
17. Незавершённый run, повторный claim ID и несовместимые cohorts отклоняются scorer.
18. Пути с пробелами обрабатываются корректно; path traversal и выход через symlink отклоняются.
19. Пользовательские branch, index и незакоммиченные файлы исходного репозитория остаются неизменными.
20. Для Docker: assertion failure отличается от collection error, timeout и flaky outcome.

Добавь ручной пример для метрик: два supported claims, два contradicted, один uncertain. Доступны один supported, один contradicted и uncertain. Ожидаются exposure 0.5, retention 0.5, contamination 0.5 и uncertain_available 1. Scorer обязан получить эти значения без доступа к логике policies.

Не заменяй Git, AST и весь engine моками в сквозных тестах. Моки допустимы для сетевого провайдера и аварийных условий Docker. Отдельно показывай, какие integration tests реально исполнялись и какие были пропущены из-за среды.

## 15. Этапы реализации и критерии завершения

| Этап | Результат | Проверяемый критерий |
|---|---|---|
| M0 | Пакет, CLI, схемы, валидация входов | Установка из lockfile; отрицательные примеры входов отклоняются |
| M1 | Git-снимки, AST и два структурных вида claims | Настоящие пары commits дают ожидаемые изменения, исходный checkout неизменен |
| M2 | Все policies, состояния, run artifacts и scorer | Offline demo сравнивает методы; ручные метрики совпадают |
| M3 | Docker probes и поведенческие claims | Parent pass, child semantic fail, environment error и flaky случай различаются |
| M4 | Replay, dependency depth и provenance ablations | Revert восстанавливает память; hidden missingness не раскрывается системе |
| M5 | Dataset manifests, annotation export, protocol freeze, bootstrap, cost reports | Независимые labels читаются только scorer; пилот запускается на доступном реальном репозитории |
| M6 | LLM prose validator и дополнительная оценка задач | Только при заданной модели, ключе, бюджете и отдельном замороженном протоколе |

В M5 создай экспорт для разметки с claim, parent/child revisions и evidence, без ответов policies. Импорт должен сохранять автора, исходный label и историю adjudication. В M5 обязателен инструментальный процесс сбора данных, но программа не может сама завершить человеческую разметку.

При нехватке Docker заверши M0–M2 и независимые части M4–M5; M3 и соответствующие результаты пометь blocked. Не объявляй все обязательные этапы завершёнными. При отсутствии API-ключа M6 остаётся optional и не блокирует обязательную программу.

В M6 дополнительная локализация кода ограничивается 30 заранее зафиксированными задачами. Каждая имеет query, commit и независимый набор допустимых файлов. Агент получает память данной policy и одинаковый доступ к текущему репозиторию. Метрики: наличие допустимого файла в top-1 и top-5, tokens и время. Фиксируются model, prompt, retrieval rule, число доступных фрагментов и общий бюджет. Пока такой протокол не зафиксирован, не генерируй числа о пользе для агента.

После каждого этапа обновляй `docs/implementation_status.md`: что реализовано, какие команды прошли, реальные ограничения, следующий этап. После последнего доступного этапа предоставь команды воспроизведения и перечень незавершённых внешних действий. Наличие файлов, зелёные unit tests и сгенерированный график сами по себе не означают завершённый эксперимент.

## 16. Критерий готовности программы

Программа готова как обязательный исследовательский прототип, когда M0–M5 реализованы, offline demo воспроизводится, реальный pilot workflow проверен, ошибки не маскируются под успешные verdicts, данные доступны для независимой оценки и нет утечки labels в исследуемый метод.

Научная работа готова к выводам только после независимой разметки, замороженного основного эксперимента и анализа ограничений. Не называй разработку программы доказательством гипотезы и не заявляй новую научную идею на основании одного этого документа.

## 17. Основания решений и ссылки

Выбрана архитектура с неизменяемыми файлами, потому что главный результат здесь воспроизводимый эксперимент. Она делает входы, состояние каждого claim и расчёт метрик доступными для проверки. SQLite можно добавить после измеренного ограничения объёма, сохранив JSONL-контракт; заранее это не требуется.

При проектировании сопоставлены два варианта: JSONL-артефакты и SQLite-журнал с транзакционным возобновлением. Основой выбран первый вариант. Из второго приняты раздельные реальные и логические расходы, общий зафиксированный ответ валидатора для одинакового запроса и запрет начислять baseline ненужный графовый анализ. Автоматическое возобновление, миграции БД и поиск преемников по сходству AST исключены. Независимая проверка вариантов также рекомендовала файловую основу. Обе оценки выполнены Codex Sol, без разнообразия провайдеров.

По сравнению с общим proposal эта версия уточняет три границы. `retired` относится к точному структурному subject, а не к доказанному отсутствию любого семантического преемника. Основная программа обслуживает фиксированный cohort. LLM и локализация остаются дополнительным этапом. Эти ограничения нужно сохранить в будущих научных выводах; текущие документы для сабмита автоматически не изменяются.

Принцип Model the Domain применён к отдельным Claim, Verdict и MemoryState: политика доступности не должна подменять доказательство истинности. Принцип Prove It Works применён к критериям приёмки: сквозной запуск и независимые ожидаемые ответы обязательны.
